I
05Capitolo I · Definizione

Un sito che parla all'agente,
invece di farsi guardare.

WebMCP permette a qualsiasi sito di esporre le proprie funzionalità come tool richiamabili da agenti AI direttamente nel browser.

Il sito dichiara cosa sa fare — "aggiungi al carrello", "crea ticket", "cerca cliente" — tramite un'API JavaScript. L'agente (Claude, Copilot, Gemini, qualunque LLM connesso al browser) invoca quei tool con parametri tipizzati.

Nessun DOM scraping. Nessuno screenshot da interpretare. Nessuna automazione fragile che si rompe al primo redesign.

Standard W3C Lato client Eredita sessione browser

II
08Capitolo II · Il problema

Oggi gli agenti vedono il web come un umano. Male.

Approccio attuale
▥

DOM scraping & vision

  • Screenshot e accessibility tree nel contesto del modello
  • Token costo enorme · latenza alta
  • Si rompe al primo redesign o A/B test
  • Ambiguità su quale bottone cliccare
  • Auth fragile, captcha, anti-bot
  • Nessuna semantica: il modello "indovina"
→
Con WebMCP
◉

Tool invocation strutturato

  • Il sito dichiara add_to_cart(sku, qty)
  • JSON Schema sui parametri · zero ambiguità
  • Riusa la logica del frontend, non la sua UI
  • Sopravvive a qualsiasi redesign
  • Eredita cookie / SSO / CSRF della sessione
  • Conferma esplicita per azioni distruttive
09Capitolo II · Posizionamento

MCP vs WebMCP.

WebMCP non sostituisce MCP. È una superficie diversa per esporre tool al modello quando l'utente è già nel browser.

MCP · Anthropic, 2024 WebMCP · W3C, 2026
TrasportoJSON-RPC su stdio / HTTPnavigator.modelContext
Dove giraServer, locale o hostedLato client, dentro la pagina
Stato & sessioneServer mantiene contestoLa pagina viva è il contesto

DiscoveryCatalogo MCP o config clientTool della pagina che l'utente sta visitando

Capitolo · III / 06
10Capitolo III

Come funziona.

Un singolo punto d'ingresso, quattro campi, mediazione utente nativa. La spec è sorprendentemente piccola.
III
11Capitolo III · L'API

navigator.modelContext. Tutto qui.

Un singolo punto d'ingresso nel browser. La pagina registra una lista di tool; ognuno dichiara nome, descrizione, input schema e una funzione execute.

Metodi principali
  • · provideContext({ tools }) — registra l'intera lista
  • · registerTool(tool) — aggiunge un tool
  • · unregisterTool(name) — rimuove un tool

Le invocazioni sono serializzate sul main thread: lo stato UI resta sincronizzato con ciò che l'agente osserva.

// Esempio minimo dalla spec W3C
if ("modelContext" in window.navigator) {
  navigator.modelContext.provideContext({
    tools: [{
      name: "add-stamp",
      description: "Aggiungi un francobollo alla collezione",
      inputSchema: {
        type: "object",
        properties: {
          name:  { type: "string" },
          year:  { type: "number" }
        },
        required: ["name", "year"]
      },
      async execute({ name, year }, agent) {
        addStamp(name, year);
        return {
          content: [{
            type: "text",
            text: "Stamp added!"
          }]
        };
      }
    }]
  });
}
12Capitolo III · Mediazione

L'utente sempre nel loop, quando conta.

Ogni execute riceve un secondo argomento agent che espone requestUserInteraction().

Da usare per conferme esplicite su azioni:

  • · finanziarie (pagamenti, rimborsi)
  • · distruttive (eliminazioni, cancellazioni)
  • · con effetti su terzi (mail, notifiche)
  • · su dati sensibili (PII, contratti)
Principio Tutto ciò che un utente prudente non automatizzerebbe va dietro requestUserInteraction. 
// Pagamento con conferma esplicita
{
  name: "checkout",
  description: "Completa l'acquisto del carrello",
  inputSchema: { /* ... */ },
  async execute({ paymentMethod }, agent) {
    const total = getCartTotal();

    const ok = await agent.requestUserInteraction(
      async () => confirm(
        `Vuoi pagare €${total}?`
      )
    );

    if (!ok) return {
      content: [{ type: "text",
        text: "Annullato dall'utente" }]
    };

    return await processPayment(paymentMethod);
  }
}
Capitolo · IV / 06
13Capitolo IV

Dove crea valore.

Otto casi d'uso ad alto impatto, mappati su settori che già spendono in agent automation: commerce, SaaS B2B, customer support, accessibilità, internal tools.
IV
14Capitolo IV · Dove crea valore (1/2)

Casi d'uso ad alto impatto.

$

Commerce conversazionale end-to-end

Tool: search_products, add_to_cart, apply_coupon, checkout. L'agente completa ordini multi-step senza simulare click. Conferma utente su pagamenti via requestUserInteraction.

→ Conversion rate su sessioni assistite, riduzione cart abandonment.

▤

Dashboard SaaS che parlano

CRM, project management, billing, analytics, ITSM. L'agente traduce l'intento in operazioni strutturate: "crea opportunità da 50k per ACME, chiusura Q3". Riduce la curva di apprendimento di tool enterprise (Salesforce, AWS, Jira).

→ Time-to-value su nuovi utenti, ticket di supporto in calo.

⚑

Self-service che chiude i casi

Tool: get_order_status, start_return, update_address, escalate_to_human. L'agente esegue flussi che oggi richiedono un operatore, con audit trail e consenso esplicito su ogni azione irreversibile.

→ Deflection rate, MTTR sui ticket di primo livello.

✈

Booking strutturato

Tool: search_flights, hold_seat, confirm_booking. Combina sessione utente (preferenze, miglia, payment methods) con esecuzione strutturata e verifiche pre-pagamento.

→ Riduzione drop-off in fasi check-out complesse.

15Capitolo IV · Dove crea valore (2/2)

Casi d'uso meno ovvi, alto valore.

◐

Interfacce parlate, non interpretate

Le tecnologie assistive ricevono azioni di alto livello (add_to_cart) invece di "clicca questo bottone". Un assistente vocale può guidare anche app difficili da navigare con accessibility tree tradizionale.

Caveat: WebMCP affianca, non sostituisce, l'accessibilità tradizionale.

⊞

Automazioni interne & userscript AI

L'estensione WebMCP raccoglie tool dalle tab aperte e li espone a Claude Desktop. Flussi tipo: "aggrega dati da queste 3 dashboard interne e mandami un riassunto". Riduce drasticamente il costo di integrazioni custom.

→ Tempo speso in copia-incolla, errori manuali.

€

Finanza e Pubblica Amministrazione

Categorizzazione transazioni, generazione report, esportazione CSV — con requestUserInteraction su qualsiasi movimento. Per PA: pratiche, scadenze, modulistica con tracciabilità nativa.

⌘

Test E2E aumentati & dev tools

Tool WebMCP usati come hook deterministici da framework di testing. IDE web (StackBlitz, CodeSandbox) e DevTools espongono run_cell, format_code, open_file invece di simulare scorciatoie.

Implicazione strategica

Chi non espone tool oggi, sarà invisibile agli agenti di domani.

Il valore si sposta su dominio e accesso privilegiato ai dati. La UI proprietaria, da sola, smette di essere una barriera competitiva.
Capitolo · V / 06
17Capitolo V

Come si fa.

Due percorsi: progettare un prodotto agent-first da zero, oppure incrementare un sito esistente con un approccio wrapper, senza rewrite.
V
18Capitolo V · Implementazione (1/2)

Da zero: nuovo prodotto, design agent-first.

  1. Mappa le intenzioniPer ogni feature, scrivi la frase che un utente direbbe ad alta voce. Quella è la firma del tool.
  2. Definisci la tool surface5–10 tool al massimo. Granularità "intent", non "click". Nomi verbo-oggetto.
  3. Schema firstJSON Schema per input e output. Tipi stretti, enum dove possibile, descrizioni ricche.
  4. Implementa executeStessa logica del frontend, esposta via navigator.modelContext. Niente duplicazione.
  5. ConfermeOgni side-effect non reversibile dietro requestUserInteraction.
  6. Tool surface policyDocumento interno: cosa esponiamo, a chi, con quali conferme. Vive col prodotto.
import { useWebMCP } from "@mcp-b/react-webmcp";

export function ProductSearch() {
  const [results, setResults] = useState([]);

  useWebMCP({
    name: "search-products",
    description:
      "Cerca prodotti per query e categoria",
    inputSchema: {
      type: "object",
      properties: {
        query:    { type: "string" },
        category: { type: "string",
                     enum: ["shoes", "bags",
                            "apparel"] }
      },
      required: ["query"]
    },
    execute: async ({ query, category }) => {
      const data = await runSearch(query, category);
      setResults(data);
      return { content: [{ type: "text",
        text: `Trovati ${data.length}` }] };
    }
  });

  return <ResultsList items={results} />;
}
19Capitolo V · Implementazione (2/2)

Su un sito già in essere. Bottom-up.

L'approccio incrementale: una feature ad alto traffico, 2–3 tool, misurare, espandere. Nessun rewrite.

  1. Audit del flusso targetTrova il flusso con drop-off alto o ticket di support frequenti. È lì che WebMCP ripaga subito.
  2. Identifica i punti di chiamataQuali funzioni JS già esistono dietro i bottoni? Spesso il tool è una riga: stesso codice, nuovo wrapper.
  3. Inietta il polyfill@mcp-b/global in tutte le pagine. Carica solo se modelContext non è nativo.
  4. Registra 2–3 tool pilotaIdealmente read-only prima (search, get_status). Costo basso, valore visibile, rischio minimo.
  5. Espandi su write con confermeSide-effect dietro requestUserInteraction finché il pattern si stabilizza.
  6. Strumenta & misuraAudit trail: chi chiama cosa, con quali parametri, esito. Per security e per prodotto.
Pattern di adozione

Wrapper,
non rewrite.

I tool WebMCP sono guscio sopra il codice esistente: chiamano gli stessi servizi, gli stessi reducer, gli stessi endpoint che il bottone della UI già chiama.

Decisioni chiave
  • · Stessa business logic UI/agente
  • · Granularità intent, non click
  • · Allowlist domini se necessario
  • · CSP/CORS invariati: gira lato client
  • · Versionare la tool surface (semver)
2–3 settimane Per pilot feature

21Capitolo VI · Perché conviene

I quattro vantaggi che pagano da soli il progetto.

Affidabilità
0 brittleness

Niente inferenza su HTML o screenshot. Il tool sopravvive a qualsiasi redesign. Nessun selettore CSS che si rompe il venerdì sera.

Token efficiency
−90% contesto

Niente accessibility tree o screenshot nel prompt. Solo lista tool e parametri. Costi modello in caduta, latenza crollata.

Riuso codice
1 sorgente

Stessa logica del frontend. Stessi servizi, stessi reducer. Una sola business logic da mantenere per UI umana e UI agentica.

Quarto vantaggio · Sicurezza

L'esecuzione resta nel sandbox del sito. Eredita auth, CSP, CORS, rate limit. Niente credenziali da gestire fuori dal browser.

Bonus · Strategico

Posizionamento "agent-ready". Effetto analogo a structured data per la SEO classica — AEO, Agent Experience Optimization.

22Capitolo VI · Rischi & mitigazioni

Cosa tenere d'occhio. Onestamente.

!

Tool poisoning

La descrizione del tool entra nel contesto del modello. Una descrizione malevola può iniettare istruzioni. Anche schema e nomi sono prompt potenziali.

Mitigazione

Code review delle descrizioni come del codice. Linting su pattern sospetti. Allowlist se la pagina include UGC.

!

Confused deputy

L'agente può essere indotto da contenuti di terze parti (commenti, prodotti, email mostrate in pagina) a invocare tool sensibili a nome dell'utente.

Mitigazione

requestUserInteraction su tutto ciò che è distruttivo, finanziario o lato terzi. Audit log con prompt originale.

!

Consenso utente

La spec attuale lascia la "trust decision" al sito stesso. Manca per ora un meccanismo standard: "il sito X vuole esporre N tool al tuo agente, autorizzi?"

Mitigazione

Banner first-party che annuncia la disponibilità di tool agentici. Opt-in esplicito per categorie sensibili.

Postura consigliata Least privilege sui tool, allowlist degli agenti dove possibile, log strutturati di ogni invocazione, conferma umana sintetizzata su azioni non reversibili. La maggior parte di questi rischi è gestibile col rigore con cui si gestisce qualsiasi superficie pubblica.

24Capitolo VI · Roadmap di sperimentazione

Come iniziare, senza farsi male.

  1. Setup ambiente · 1 giornoLeggere proposal W3C + esempi. Installare estensione MCP-B + Claude Desktop. Provare un esempio del repo.
  2. Mini-app pilota · 3–5 giorniUna piccola app React con polyfill @mcp-b/global. 3 tool che coprano il flusso più frequente. Validazione: estensione → Claude Desktop, oppure Chrome 146 Canary + flag EPP.
  3. Use case su prodotto cliente · 2–3 settimane1 flusso ad alto traffico/dolore. Definizione tool surface (5–10 tool). Implementazione wrapper sul codice esistente. Conferme su azioni sensibili.
  4. Tool surface policy · 1 settimanaDocumento di governance: quali tool, a chi, con quali conferme, come versionarli, come revocarli. Vive col prodotto.
  5. Strumentazione & KPI · continuoAudit log delle invocazioni. Misure: tasso d'uso, completamento azione, errori, conferme negate. Confronto con baseline pre-WebMCP.
  6. Pilot in produzione behind flag · 4–8 settimaneRilascio a coorte limitata (utenti opt-in, dipendenti, beta). Misurazione. Decisione GA.
