Come implementare
WebMCP davvero.

Anatomia della demo Bella Roma Coffee: come abbiamo reso un sito React invocabile da Claude in 165 righe di codice client, senza estensione, su browser nativo e su browser stable.

Stack React 18 · Vite 6 · Zustand · TypeScript 5 API navigator.modelContext + relay locale Tempo di lettura ~14 minuti
I
Capitolo I · Vista d'insieme

L'architettura,
in una pagina.

Un sito React esistente, sei tool registrati con navigator.modelContext, due bridge intercambiabili verso Claude Desktop, un unico modale di conferma per le azioni distruttive. Tutto in-page, nessuna estensione.

La demo Bella Roma è un coffee shop fittizio: catalogo, carrello, coupon, checkout. Le sei funzioni — search_products, add_to_cart, remove_from_cart, apply_coupon, get_cart, checkout — sono la stessa identica logica che usa l'utente cliccando i bottoni. WebMCP è solo un guscio sopra lo store Zustand.

Il problema non è "esporre le funzioni" — è esporle ovunque: su Chrome Canary che ha la spec nativa, e su Chrome stable che non ce l'ha. Abbiamo scritto un piccolo orchestratore di 80 righe che rileva il browser e instrada al bridge giusto, senza far cambiare nulla all'utente.

§ 1.1 I due bridge

Native · Chrome 146 Canary
relay-client.ts

La pagina apre un WebSocket direttamente verso 127.0.0.1:9333, parla il protocollo del relay, dispatcha le invoke localmente.

  • Usa navigator.modelContext.registerTool (W3C spec)
  • 165 LoC client · nessuna dipendenza extra
  • Reconnect con backoff 2s → 30s
  • Indicatore "nativo (Canary)" 🟢 + "native WS (open)" 🔵
Polyfill · Chrome stable / qualsiasi
embed CDN

Il polyfill @mcp-b/global installa navigator.modelContext; l'embed @mcp-b/webmcp-local-relay da CDN inietta un iframe che apre il WebSocket per noi.

  • Usa provideContext({tools}) (API polyfill)
  • Solo 1 import npm + 1 <script> CDN
  • Nessuna estensione browser richiesta
  • Indicatore "Polyfill MCP-B" 🟡 + "embed CDN" 🟣

Punto chiave Lo stesso sito gira su due path completamente diversi senza che l'utente lo sappia. II
Capitolo II · La tool surface

Sei tool. Granularità intent, non click.

Una buona tool surface non rispecchia i bottoni della UI: rispecchia il linguaggio con cui l'utente esprime cosa vuole fare.

Le sei firme sotto coprono per intero il flusso del coffee shop: scoperta del catalogo, manipolazione del carrello, applicazione coupon, lettura stato, conferma ordine. Niente "click_button", niente "fill_input": l'agente parla in operazioni di business, non in eventi DOM.

Tool Cosa fa Conferma utente
search_products Filtra il catalogo per category (espresso, filtro, decaf, latte), max_price, o testo libero. Solo lettura, idempotente. no
add_to_cart Aggiunge product_id in quantity (1–10). Reversibile via remove_from_cart. JSON Schema con required: ["product_id","quantity"]. no
remove_from_cart Rimuove una riga. Risponde con errore se l'item non era presente. no
apply_coupon Applica BENVENUTO (-10%) o STUDENTI (-20% max €5). Lo store ricalcola subtotale, sconto, totale. no
get_cart Ritorna stato corrente: items, subtotale, sconto applicato, totale. Read-only. no
checkout Conferma l'ordine, svuota il carrello. Side-effect non reversibile: passa attraverso requestUserInteraction che apre il modale React. sì

§ 2.1 Forma di un tool — il contratto

Ogni tool è un oggetto con quattro campi: name, description, inputSchema (JSON Schema), e una funzione execute. Il secondo argomento di execute è l'agent, che espone requestUserInteraction.

export type Tool = {  name: string;  description: string;  inputSchema: Record<string, unknown>;  execute: (args: Record<string, unknown>, agent?: Agent) => Promise<ToolResult>;}; // add_to_cart — un esempio reale{  name: "add_to_cart",  description: "Aggiunge un prodotto al carrello in una certa quantità.",  inputSchema: {    type: "object",    properties: {      product_id: { type: "string", description: "L'id del prodotto" },      quantity:   { type: "integer", minimum: 1, maximum: 10 },    },    required: ["product_id", "quantity"],  },  async execute(args) {    const { product_id, quantity } = args as { product_id: string; quantity: number };    const ok = useCartStore.getState().addItem(product_id, quantity);    if (!ok) return err(`Prodotto "${product_id}" non trovato.`);    const msg = `Aggiunto: ${formatProduct(product_id, quantity)}.`;    useCartStore.getState().logToolCall("add_to_cart", args, msg);    return ok(msg);  },}

Tre regole che hanno guidato il design

  • Nomi verbo-oggetto. add_to_cart, non cart_add. L'agente li interpreta come azioni, non come endpoint.
  • Schema stretto. enum sulle categorie, minimum/maximum sulle quantità. Errori prima dell'esecuzione, meno round-trip col modello.
  • Output testuale ricco. "Aggiunto: Espresso x2 (€4.00)." — l'agente riusa il testo per parlare con l'utente senza dover interpretare strutture.
III
Capitolo III · Setup

Ambiente, in cinque minuti.

Tre cose: il sito React, Claude Desktop con il relay locale come server MCP, e (opzionalmente) Chrome 146 Canary col flag EPP per il path nativo. La presenza simultanea non serve — uno dei due basta.

§ 3.1 Sito React

# dalla root del repo
npm install
npm run dev    # http://localhost:5173

Il dev server di Vite serve il sito sulla 5173. Aprilo: vedrai i prodotti e il carrello. Senza fare altro, sei già a metà strada — il polyfill @mcp-b/global è una dipendenza npm ed espone navigator.modelContext nella pagina al primo import.

§ 3.2 Claude Desktop + relay locale

Apri (o crea) la config di Claude Desktop. Su macOS: ~/Library/Application Support/Claude/claude_desktop_config.json. Aggiungi il relay come MCP server stdio:

{  "mcpServers": {    "webmcp-local-relay": {      "command": "npx",      "args": ["-y", "@mcp-b/webmcp-local-relay@latest"]    }  }}

Riavvia Claude Desktop completamente: ⌘Q e riapri. Chiudere la finestra non basta. Il relay viene lanciato da Claude come child process via stdio, e in autonomia apre un WebSocket server su 127.0.0.1:9333 per le tab del browser.

Verifica lsof -nP -i :9333 — devi vedere una riga node · LISTEN. Quando una tab si connette, vedrai anche Google · ESTABLISHED. Se manca il LISTEN, Claude non ha picked up la config: ricontrolla il path e riavvia.

§ 3.3 Apri la demo

http://localhost:5173/?relay=true

Il query param ?relay=true attiva il bridge. In header due indicatori:

  • Connessione — 🟢 nativo (Canary) · 🟡 polyfill MCP-B · ⚪ nessun agente
  • Bridge — 🔵 native WS open · 🟣 embed CDN · 🟠 connecting · 🔴 error · ▫ off

Su Canary EPP vedrai 🟢 + 🔵. Su Chrome stable vedrai 🟡 + 🟣. Funziona uguale.

IV
Capitolo IV · Detection

Capire chi abbiamo
davanti.

Prima di registrare i tool dobbiamo sapere se il browser è nativo (Canary EPP) o se ci serve il polyfill. La detection è in 20 righe, ma c'è una sottigliezza: il solo 'modelContext' in navigator non basta. Alcuni setup caricano il polyfill come side-effect anche dove la nativa esiste; per distinguere usiamo constructor.name.

export type WebMCPMode = "native" | "polyfill" | "unavailable"; function detectKind(mc: object): "native" | "polyfill" {  // Native Chrome: constructor.name === "ModelContext"  // Polyfill MCP-B: "BrowserMcpServer" + espone provideContext/callTool.  if (mc.constructor?.name === "ModelContext") return "native";  if ("provideContext" in mc || "callTool" in mc) return "polyfill";  return "native";} export async function ensureWebMCP(): Promise<WebMCPMode> {  if (typeof window === "undefined") return "unavailable";  const existing = window.navigator.modelContext;  if (existing) return detectKind(existing);  // Nativo non c'è: importa il polyfill (dynamic import, no overhead se non serve).  try {    await import("@mcp-b/global");    const installed = window.navigator.modelContext;    return installed ? detectKind(installed) : "unavailable";  } catch { return "unavailable"; }}

L'import() dinamico è importante: su browser che hanno la nativa, il polyfill non viene mai scaricato. Vite produce un chunk separato, caricato solo se serve.

V
Capitolo V · L'adapter

Un guscio sopra lo store.

I tool WebMCP non duplicano la logica: chiamano lo stesso store che usano i bottoni della UI.

La regola d'oro: la business logic vive in un solo posto. Per noi è Zustand (src/store/cart.ts). I bottoni della UI fanno useCartStore.getState().addItem(id, qty); il tool WebMCP fa useCartStore.getState().addItem(id, qty). Identico.

Questo significa che la UI manuale e la UI agentica passano dagli stessi update reattivi — clicchi il bottone o l'agente invoca add_to_cart, il carrello si aggiorna allo stesso modo, con le stesse animazioni di Framer Motion.

§ 5.1 Registrazione dual-API

L'API nativa W3C ha registerTool(tool) per tool singolo. Il polyfill ha provideContext({tools}) per la lista intera. Una sola funzione di registrazione, due rami:

let registered = false; export async function registerTools(): Promise<void> {  if (registered) return;                          // idempotente  const mc = navigator.modelContext;  if (!mc) return;  const tools = buildTools();   // Native Chrome: registerTool per tool. Dedup via getTools() se disponibile.  if (typeof mc.registerTool === "function") {    const existing = await listExistingToolNames(mc.getTools);    for (const t of tools) {      if (existing.has(t.name)) continue;      await Promise.resolve(mc.registerTool(t));    }    registered = true; return;  }   // Polyfill: provideContext fa il replace della lista.  if (typeof mc.provideContext === "function") {    mc.provideContext({ tools });    registered = true;  }}
Idempotenza Un flag registered impedisce doppie registrazioni quando React re-monta (HMR, StrictMode). Per la native API c'è un secondo livello: getTools() dice quali tool sono già lì, e saltiamo i duplicati. Senza questo, ogni hot reload aggiunge sei tool nuovi.
VI
Capitolo VI · Bridge native

165 righe
che parlano col relay.

Su Canary, l'API nativa navigator.modelContext espone i tool al browser, ma non li manda automaticamente a Claude Desktop. Serve un trasporto. La nostra scelta: aprire un WebSocket direttamente verso webmcp-local-relay e parlarci il suo protocollo.

Niente estensione, niente embed CDN. Una sola classe di stato e quattro messaggi: server-hello, hello/accepted, invoke, result. Più ping/pong per il keep-alive.

const tabId = crypto.randomUUID(); const connect = () => {  setState("connecting");  ws = new WebSocket("ws://127.0.0.1:9333");  ws.addEventListener("message", onMessage);  ws.addEventListener("close", () => { setState("closed"); scheduleReconnect(); });}; const onMessage = async (ev) => {  const msg = JSON.parse(ev.data);  switch (msg.type) {    case "server-hello":      send({ type: "hello", tabId, origin: location.origin,             url: location.href, title: document.title });      send({ type: "tools/list", tools: tools.map(serializeTool) });      break;    case "hello/accepted":      setState("open"); reconnectMs = INITIAL_RECONNECT_MS; break;    case "ping": send({ type: "pong" }); break;    case "invoke": {      const result = await dispatch(tools, msg.toolName, msg.args ?? {});      send({ type: "result", callId: msg.callId, result });      break;    }  }};

La dispatch è la parte più interessante: non usiamo executeTool del modelContext nativo. Pesca il tool dalla lista locale e chiama tool.execute(args, fakeClient) direttamente. Questo ci dà tre cose:

  1. Indipendenza dal vendorSe l'API native cambia o viene rinominata, il dispatch resta. Il contratto è solo: la Tool ha un execute(args, agent).
  2. Stessa code-path delle due APIIl polyfill chiama tool.execute. La nostra dispatch chiama tool.execute. Un singolo set di test copre entrambi.
  3. Conferme controllateIl fakeClient.requestUserInteraction è una passthrough che chiama subito la callback. Il modale React di conferma si apre lo stesso (via event bridge), perché è registrato dal lato React e requestCheckoutConfirmation è agnostico.

§ 6.1 Reconnect che si comporta bene

Backoff esponenziale 2s → 30s. Senza, se Claude non è in esecuzione, la tab tenta una connessione al secondo per ore e satura la console. Con backoff: due tentativi nei primi 6 secondi, poi sempre più diradati. Quando Claude torna, ci si riconnette in massimo 30 secondi e l'indicatore va a 🔵 open.

VII
Capitolo VII · Conferma esplicita

L'utente sempre nel loop,
quando conta.

Sui sei tool, cinque sono privi di conferma — sono operazioni reversibili o di sola lettura. Il sesto, checkout, è l'unico irreversibile: passa attraverso agent.requestUserInteraction e mostra un modale React. Senza la conferma, niente ordine.

{  name: "checkout",  description: "Conferma l'ordine. Richiede conferma esplicita dell'utente.",  inputSchema: { type: "object", properties: {} },  async execute(_args, agent) {    const s = useCartStore.getState();    if (s.items.length === 0) return err("Il carrello è vuoto.");    const total = s.total();    const { requestCheckoutConfirmation } = await import("./checkout-bridge");    const ask = () => requestCheckoutConfirmation(total);     // Se l'agent espone requestUserInteraction (spec W3C), passa di lì.    // Altrimenti fallback diretto al bridge — il modale si apre comunque.    const confirmed = agent?.requestUserInteraction      ? await agent.requestUserInteraction(ask)      : await ask();     if (!confirmed) return ok("Pagamento annullato dall'utente.");    const result = useCartStore.getState().checkout();    return ok(`Ordine confermato! Totale: €${result.total.toFixed(2)}.`);  }}

§ 7.1 Il piccolo event-bridge

Il tool è codice TS puro: non può montare un modale React. Allora abbiamo checkout-bridge.ts, dieci righe di event-passing. Il componente CheckoutModal registra un listener; il tool chiama requestCheckoutConfirmation(total) e attende la promise.

type Listener = (total: number, resolve: (ok: boolean) => void) => void;
let listener: Listener | null = null;

export function setCheckoutListener(fn: Listener | null) { listener = fn; }

export function requestCheckoutConfirmation(total: number): Promise<boolean> {
  if (!listener) return Promise.resolve(window.confirm(`Pagare €${total.toFixed(2)}?`));
  return new Promise((resolve) => listener!(total, resolve));
}

Il fallback a window.confirm è la rete di sicurezza: se il modale non è montato (smoke test, errori di rendering), il pagamento può comunque essere confermato. Importante in demo dal vivo.

Principio Tutto ciò che un utente prudente non automatizzerebbe va dietro requestUserInteraction. Per noi: solo checkout. Per un CRM: anche delete cliente, invio email, modifica contratto. La lista vive col prodotto.
VIII
Capitolo VIII · Demo viva

La prova dei sessanta secondi.

In Claude Desktop, con relay attivo e tab Bella Roma aperta, chiedi:

  1. "List the connected WebMCP sources"Deve apparire la tab Bella Roma Coffee con i sei tool. Se non appare: rileggi §3.2.
  2. "Ordina 2 espresso e 1 cappuccino, applica BENVENUTO e fai checkout"L'agente invoca add_to_cart due volte, apply_coupon, poi checkout. Il modale si apre. Confermi. Ordine completato.
  3. "Mostrami solo i caffè sotto i 2 euro"Tool: search_products con max_price: 2. Risposta testuale formattata, niente effetti collaterali.
  4. "Svuota il carrello e ricomincia"Loop di remove_from_cart sugli item presenti. Tool Activity Log mostra ogni invocazione in tempo reale.

§ 8.1 Il Tool Activity Log

Pannello in basso a destra, sempre visibile. Per ogni invocazione mostra: nome tool, args JSON, risultato testuale, timestamp. Letto da useCartStore: ogni execute chiama logToolCall(name, args, result) dentro lo store. Niente magia, solo un array che cresce.

È il salvavita della demo dal vivo: se Claude sembra non rispondere, l'Activity Log ti dice subito se il tool è stato chiamato (problema nel modello / nella conferma) o no (problema di trasporto / registrazione).

IX
Capitolo IX · Anatomia del repo

Dove vive cosa.

Tutto il codice rilevante a WebMCP è in src/lib/. La separazione tra lib (pura, testabile) e components (React) è netta — i tool non importano mai componenti, i componenti non importano mai bridge.

src/lib/webmcp.ts
Adapter · core
buildTools() ritorna le sei definizioni, registerTools() sceglie tra registerTool nativo e provideContext del polyfill. Idempotente.
src/lib/polyfill.ts
Detection
ensureWebMCP() ritorna "native" | "polyfill" | "unavailable". Distingue via constructor.name, import del polyfill solo se serve.
src/lib/relay.ts
Orchestratore
connectRelay(mode) instrada al bridge corretto. Legge ?relay=true. Inietta lo script CDN per il path polyfill, import dinamico per il native.
src/lib/relay-client.ts
Bridge native
Protocollo relay completo: WebSocket verso 127.0.0.1:9333, hello, tools/list, invoke/result, ping/pong, reconnect con backoff. Espone onRelayState.
src/lib/checkout-bridge.ts
Event-bridge
Passaggio tra il tool checkout (logica) e il CheckoutModal (UI). Listener + Promise. Fallback a window.confirm se il listener non è registrato.
src/lib/products.ts
Dati
Catalogo in-memory (12 prodotti), tabella coupon. Niente backend: refresh della pagina = stato pulito. Perfetto per demo.
src/store/cart.ts
Single source of truth
Zustand store: items, coupon, activity log. Azioni addItem, removeItem, applyCoupon, checkout. Stessa API per UI e tool.
src/App.tsx
Bootstrap
Effect che chiama ensureWebMCP → registerTools → connectRelay. Espone gli stati al Header per i due indicatori (🟢/🟡, 🔵/🟣).

§ 9.1 Le cinque cose da capire

  1. buildTools()Lì vivono le sei firme + JSON Schema + execute. Inizia da qui per aggiungere un tool.
  2. useCartStoreSingle source of truth. Ogni cambiamento di stato deve passare di qui. Niente state in component.
  3. ensureWebMCPSa quale browser hai davanti. Senza questo, registerTools chiama l'API sbagliata.
  4. connectRelayDecide se aprire WS in-page (native) o caricare l'embed (polyfill). Indipendente da registerTools.
  5. relay-client.tsLa parte non-banale del nostro codice. È un client MCP completo in 165 righe.

Capitolo X · Portare lo schema altrove

Su un sito tuo, in sei passi.

L'architettura della demo è progettata per essere copiata: poche unità, contratti piccoli, dipendenze esterne minime. Per portarla su un altro sito basta sostituire la tool surface e lo store.

  1. Mappa intenti utentePer ogni feature ad alto traffico, scrivi la frase che un utente direbbe ad alta voce. Quella è la firma del tool. Mira a 5–10 tool, granularità "intent" non "click".
  2. Identifica il single source of truthRedux, Zustand, MobX, context — qualunque esso sia, è lì che vivono le azioni che la UI invoca. Quel codice è già il tuo "execute".
  3. Sostituisci il buildToolsStessa struttura: name, description, inputSchema, execute che chiama lo store. Cambia solo cosa fa.
  4. JSON Schema strettoenum dove possibile, minimum/maximum per i numerici, required esplicito. Errori prima dell'invocazione, meno round-trip col modello.
  5. Marca le azioni distruttiveCancellazioni, pagamenti, mail, modifiche a dati di terzi. Per ognuna: agent.requestUserInteraction(askConfirm). Audit log delle decisioni.
  6. Pilota dietro feature flagCaricamento polyfill condizionale. Rollout a coorte (dipendenti, beta). KPI: tasso d'uso tool, completamento azione, conferme rifiutate.

Cosa NON serve cambiare

  • polyfill.ts — detection generica, funziona ovunque
  • relay.ts — orchestrazione bridge agnostica
  • relay-client.ts — protocollo standard del relay
  • checkout-bridge.ts — utile per qualsiasi conferma modale, basta rinominare
  • Indicatori di Header — funzionano con qualunque tool registrato
Tempo stimato Per un'app React esistente, con uno store ben isolato: 2–3 giornate per 3 tool pilota, 1–2 settimane per una tool surface completa con conferme e Activity Log. La parte di dominio è quella che pesa, non il bridge.
